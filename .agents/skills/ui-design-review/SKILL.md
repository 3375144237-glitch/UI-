# Figma 与 App 界面验收

当用户提供设计稿和 App 截图，并要求检查界面还原情况时，使用本 Skill。

## 开始前

1. 创建文件或新的验收目录前，完整阅读 workspace 中的《问题与报错日志.md》。
2. 按批次收集 Figma 链接或设计稿、截图文件夹、设备名称和 REM/PX 实现方式。PX 另需设备自身 @2x 目标宽度，以及截图已为 @2x 的声明或截图倍率；REM 按宽 720px 等比处理。共用信息只收集一次；页面名称、可见状态和设计稿配对由 Codex 逐张识别、记录，不要求用户逐页填写。不得按机型名称或物理分辨率猜倍率。
3. 推荐把待比较的设计稿放在 `screenshots/design/`，把人工手机截图放在 `screenshots/device/`。也可以直接使用聊天附件的本机路径；路径传给命令后，程序会将原图副本收进验收目录。两个输入目录中的图片和 `outputs/` 报告默认被 Git 忽略，不会随代码提交。
4. 保留用户提供的原图，不覆盖、不修改。每轮验收使用新目录：`outputs/design-review/<日期>/<页面-设备>/`。原图副本放在该目录的 `inputs/`，归一后的比较图、差异预览、局部证据图、`review.json` 和 Excel 报告也放在该轮目录中。
5. 某批次必需的缩放信息缺失或冲突时，暂停该批次的缩放处理，用中文集中列出待确认项；其他信息完整的批次可继续。
6. 先检查 Figma 文件的页面列表：同一链接已有对应“<项目名>验收”页时直接复用，不新建重复页；没有时才新建，用户另给验收文件/页时沿用其地址和名称。原设计页不改。把设计稿和设备图分批放入验收页；逐模块/元素移动到对应设计位置，尽量无缝重合。每批完成对位、问题登记和证据归档后再导下一批；检查图层与画布确认内容已落位，不得停在图片导入/放置状态。若 Figma 提示未同步，记录本地状态且不宣称共享链接可见，不主动触发同步或重连。

一个设备截图文件夹按用户说明视为同一设备；该文件夹内文件名可以没有页面含义。保留原文件名，用序号辅助整理，不按文件名或分辨率推断页面或缩放倍率。用户提供该文件夹对应的设备和缩放信息即可。

## 多页面批量验收

- 用户可提供一个包含多页面截图的文件夹，不必重命名或列出各页面/业务状态。Codex 先清点图片，保留原文件名并为每张分配唯一编号；再结合 Figma 画板、标题、文案和布局识别页面及截图可见状态。不要从静态截图猜测隐藏的登录、权限或业务条件；无法确定的状态写“状态待确认”。
- 在本批次输出目录维护 `配对与进度.md`，逐张记录编号、原文件相对路径、页面/可见状态、Figma 画板链接或设计图片、长稿区段、匹配依据、把握程度、处理状态和结果目录。名称是工作标签，Figma 节点或设计图片路径用于追溯；不因名称相同就合并不同画板。
- 配对表中的每张截图必须能追溯到具体设计画板/区段和原始截图；无对应设计稿、状态无法判断或配对不唯一时标待确认，不把它记作已验收。
- 每个不同的 Figma 页面分配一个稳定页面组编号，如 `P08`。同一张长设计稿被多张设备截图覆盖时，所有对应区段共用该页面组编号；该页问题按 `P08-01`、`P08-02` 连续编号。相同页面的不同截图可以各自保留验收目录，但须在 `页面问题汇总.md` 按页面集中索引。跨页面共享组件问题单独编号（如 `NAV-01`），列出受影响页面。
- 唯一明确的配对直接验收；相似页面、重复模块、多个设计版本或缺少对应设计时，标为“待确认”，集中提供带截图编号的候选及最少必要问题。先继续其余已明确配对的截图，不要求用户确认整张配对表。
- 多图可分组处理，每组完成就更新进度。收尾核对每张输入图均有“已验收”“待确认”或“未处理及原因”的记录，并汇总数量；没有问题的已验收截图也要记录。没有截图的页面/状态不能算已验收。
- 页面识别与配对由 Codex 执行；现有 `compare` 命令每次只处理一组配对，不会独立识别整个文件夹。`--page` 由 Codex 按证据填写，无法确定的状态保留待确认；用户手动运行时也可省略该可选参数。

## 多张截图对应长设计稿

- 先逐张查看设备截图，再在长设计稿中寻找对应纵向区段。依据独特标题/文案、图标、图片、组件顺序和布局锚点定位；滚动位置本身不作为匹配依据。
- 整理配对清单：设备截图原文件名、对应设计稿起始纵坐标与区段、页面/状态、匹配依据、把握程度。明显唯一的匹配可继续处理；重复模块、相似页面或找不到足够锚点时标为“待确认”，列出候选区段，不强行配对。
- 按每张截图处理一组配对。长稿区段的纵坐标使用设计稿 @2x 像素坐标；运行 `compare` 时传入 `--design-y <起始纵坐标>`，工具从该位置裁取与归一后设备截图等高的设计稿区段。该区段坐标会记录在验收信息中。每张截图使用独立输出目录。
- 若某张截图在长稿中跨越相邻区段，可按其实际连续范围选择起点；不要把不连续的设计区域拼接后伪装成整页。可用前后相邻截图验证滚动连续性和重复内容的位置。
- 仅当裁出的设计稿区段与设备截图归一后尺寸相同才运行像素差异定位。PX 设备宽度不同于720px时，不拉伸720px设计稿；根据 Figma 自适应规则判断，规则不足的横向差异列为待确认。

## 处理截图

设计稿画板本身宽 720px，这已是本项目 @2x 验收基准；手动导出选 1×，确认图片宽 720px，不再选 2×。也可先提供 Figma 链接，由 Codex 经可用连接读取画板并核对参考图实际尺寸；无法读取或无法取得合适参考图时，再请用户补充导出图。

- REM：运行命令时使用 `--mode rem`。程序会把设备截图副本等比缩放至宽 720px，高度随比例变化。
- PX：使用 `--mode px`，并填写用户确认的设备自身 @2x 宽度 `--target-width`。如果截图已经是该设备的 @2x 图，增加 `--already-2x`；否则填写用户确认的截图倍率 `--screenshot-scale`。程序会检查倍率推算结果是否与目标宽度吻合。
- 不得拉伸设备图或修改原图。全屏红色 50% 叠图只是初始定位参考，不能当作验收结果。将设备图副本裁成单个模块/元素后，把对应裁片移到设计稿的对应模块；按相同文字、图标、边缘或中心锚点调位置，尽可能让轮廓与字形无缝重叠。裁片只移动、不缩放、不重排内部元素；无法重合后再判断尺寸、周围间距或位置差异。PX 按用户提供的换算尺寸处理；REM 先把整张设备截图等比例缩到设计稿宽度，再裁模块。所有位移和测量都记录为处理后设备截图 @2x 像素。
- 验收弹窗时先从设备截图中独立裁出弹窗，只比较弹窗与设计稿弹窗。将两张弹窗裁图的顶部边缘对齐，不使用状态栏、屏幕顶部或整屏位置作锚点；弹窗内部仍要逐模块/逐元素移动对位。
- 生成每条问题的局部证据板：包括设计稿对应区域、带问题编号的设备原图裁片，以及已移动到设计锚点上的红色 50% 叠图。问题截图必须来自同一设备原图，并将其原图 bbox、设计区域、裁片目标位置写进 `review.json`。整屏叠图、单张红图或没有设计参照的设备裁片不能代替问题证据。
- 长设计稿对应单张设备截图时，增加 `--design-y <设计稿@2x纵坐标>`；工具会从该纵坐标起裁取与处理后设备截图同高的参考区段。只有明确匹配到设计稿区段后才使用此参数。

REM 命令示例：

```bash
.venv/bin/python scripts/ui_review.py compare --design screenshots/design/page.png --device screenshots/device/page.png --mode rem --device-name "设备名称" --page "首页/默认态" --out outputs/design-review/YYYY-MM-DD/首页-设备
```

PX 命令还需增加 `--target-width <设备自身@2x宽度>`，并根据截图情况选择 `--already-2x` 或 `--screenshot-scale <用户确认的截图倍率>`。

程序会保留输入原图，并生成处理后的图片、三种锚点叠图、`review.json`、差异预览图和 `report.xlsx`。`align` 可调整当前叠图并更新复核记录：

```bash
.venv/bin/python scripts/ui_review.py align --session <验收目录> --alignment left --offset-y 0
.venv/bin/python scripts/ui_review.py align --session <验收目录> --alignment right --offset-y 12
.venv/bin/python scripts/ui_review.py align --session <验收目录> --alignment center --offset-y 0
```

纵向偏移用归一后设备图 @2x 像素，正数下移。整屏先左对齐调纵向，再右对齐；居中模块用中心锚点。随后在 Figma 里逐模块/元素裁切并独立移动设备副本，避免半透明叠色。整屏对齐不能替代局部对位；弹窗只按弹窗顶部锚点。

## 人工检查与记录

### 固定优先级与重复模块规则

每个页面严格按以下顺序检查，前一层未完成不得用后一层替代：

1. **P0-功能**：确认大的模块、入口、状态和核心内容没有缺失；截图没有覆盖的状态不得推断为通过。
2. **P0-模块外观**：检查每个大模块的宽高、布局、样式、圆角、边框、阴影和与周围模块的间距。
3. **P0-模块内容**：逐项核对模块内部的文案、图片、图标、控件、数量、顺序和状态；瀑布流、列表、统计卡等重复内容按实例编号逐个核对，不用“整体一致”代替实例检查。实例可用序号、标题、图片特征、图标和所在行列定位。
4. **P0-素材容器**：分别测量图片容器、图片可见边界、icon 节点框和 icon 可见轮廓；节点框 48×48 不代表图形本身是 48×48。缺失、尺寸、位置、裁切和比例分别登记。
5. **P0-文字**：固定文案核对内容、字体、字号、字重、行高、换行和对齐；设计稿中可配置的数字只核对字体样式和字号，不比较具体数字。
6. **P0-适配与大间距**：确认设备截图已按目标设备适配。间距差超过 4px 且明显破坏页面布局时记 P0；不能重合时分别判断元素尺寸、周围间距或位置。
7. **P1-小间距**：间距有差异但在 4px 内，且没有达到 P0 的布局影响，记 P1。

同一页面出现多个独立错误时，使用同一页面组编号并连续编号，例如 `P08-01`、`P08-02`；不要把多个问题合并成一句模糊描述。一个页面内 icon 尺寸、文案字号、容器位置和相邻间距应分别有自己的 bbox 和证据。

### 字体识别与替代方案

Figma 接口能返回字体属性时，记录字体家族、字重、字号、行高和文字图层节点；接口只返回图层名称或图片时，不得根据视觉猜测字体名称。请用户提供可编辑文字图层链接，或截取右侧 Typography/字体属性区域；如果文字已转曲、栅格化或导出成图片，只能记录“字体待确认”，并把设备与设计稿的字形差异作为待确认项。字体识别不到时仍检查字形粗细、字号视觉、行高、换行、字距和对齐，但测量值要标估算。

- 自动差异框和并排图只是线索。逐张核对用户指定的 Figma 画板、组件/Token、页面内容和 App 状态；无法像素差分时仍须人工检查，不能留空。静态文案、规则、选项映射、内容数量/顺序、菜单和状态逐项比对；动态数值不比具体值，但检查字段、字体、占位、对齐和换行。运行时图片可忽略素材内容时，仍检查尺寸、比例、裁切和遮挡。
- 维度包括布局对齐、尺寸/间距、颜色、字体与行高、圆角/边框/阴影、图标、图片裁切、遮挡、截断和状态；也检查系统字体/抗锯齿、状态栏、安全区、滚动和加载。逐项核对容器内外边距、控件间距、卡片与按钮尺寸、标签留白、选项区底部空间，以及人工验收记录中的素材缺失/新增、溢出和中文字体粗细。每项记录通过、不通过或待确认。能读节点/Token 时记录设计值；截图记录实际值和差值，否则标估算/待确认。
- 列表、瀑布流、统计卡、菜单和工具栏按实例逐项匹配设计节点与设备图。分别量容器、icon 节点框、图形可见边界、设备 bbox、尺寸差及中心偏移；48×48 节点框不代表图形铺满。缺项与现存 icon 尺寸问题分开记录，不用整体结论替代逐项检查。
- 对位时优先让同一元素重合；若内容锚点对齐后容器仍不合，分别记录“元素尺寸”“周围间距”或“位置”，并写明实际、设计依据、差值及相邻正确部分。可简写“与设计稿保持一致”；表格备注按用户要求留空，设计依据用单独截图/字段提供。可配置数字只检查字体样式和字号。
- 有 Figma 设计变量/Token、组件规范或标注时，先读取并作为颜色、间距、字号和圆角的判断依据；没有这些资料时，只记录截图可直接支持的观察和测量，不猜测 Token 名称或源码配置。
- 同一根因影响多页时合并并列出页面/状态；同一页面多个独立差异分别编号和框选，不合并成模糊问题。每条使用实际来源截图的 `bbox` 并标原文件名；设计版本、规则或状态未确认时标“待确认”，说明待确认项，不直接下修复结论。
- 每轮结束生成 `页面问题汇总.md`：按页面组列出涉及截图、问题 ID、状态、报告目录及待确认事项；让研发能先定位页面，再查看该页面的全部问题和对应证据。进度文件统计验收覆盖数量，总表统计实际问题数量，两者不要混淆。每个 `review.json` 的 `review_status` 在人工完成逐项核对后更新为对应状态；零问题默认不等于通过。
- 汇总中的每个问题都要链接到其来源截图对应的局部标注证据和并排对照图；证据必须来自该条问题记录中的同一设备截图，并能看清问题编号和位置。不能只给整批截图总览、只给问题文字，或用另一张截图代替。
- 对“已验收、未发现明确差异”的截图，也要在汇总中列出原文件名、对应设计稿和可打开的并排对照图；不可留空或只写“无问题”。待确认与未处理截图须单独列明原因，不得混入无问题数量。
- 不得仅凭截图像素推断源码字号或 dp/pt 数值。测量坐标统一记为“处理后设备截图 @2x 像素坐标”；无法确认的测量值注明“估算”。
- 在 `review.json` 的 `findings` 列表中添加或修改问题。每个问题都要有稳定且唯一的 `id`，并填写设备截图上的问题框 `bbox`：`x`、`y` 是左上角坐标，`width`、`height` 是框的宽和高。坐标使用上述 @2x 像素单位。
- 有证据时用以下字段补充问题详情：`category`（问题类别）、`affected_pages`（受影响页面/状态列表）、`description`（问题描述）、`design_basis`（设计依据）、`expected`（设计预期）、`actual`（实际表现）、`measurement`（测量结果或差值）、`recommendation`（修复建议）。不要为了填满字段而猜测。
- 问题还未核实是否违反设计时，状态保持“待确认”；确认问题后再按情况设置“待修复”“修复中”“已修复”或“不修复”。优先级使用“待评估”或 P0 至 P3。所有面向设计、产品和研发的结论、备注及建议均使用中文。
- `review.json` 与局部证据准备好后，依当前电子表格 Skill 使用 `@oai/artifact-tool` JS 创建 `.xlsx`；旧的 `ui_review.py report/batch-report` 不作为新交付表格作者。每项验收记录包含设备、问题截图、描述、优先级、状态和备注，并嵌入同源问题证据；详情表记录设计依据、实际表现、测量、建议及 bbox。批次表还需有截图清单，逐张记录来源、设计配对、处理状态和问题数。
- Excel 可直接编辑。重建同一批次前先读取旧表并保留手改字段；不得静默覆盖。新截图使用新验收目录；问题 ID、状态、bbox、设备截图和证据须与 `review.json` 及 Markdown 汇总逐项一致。
- 用户提供修复后截图时，按相同缩放信息复查。仅有代码改动、没有新截图证据时，不得将问题标记为“已修复”。

### 完成前核对

- 输入清单中的每张截图都恰好有一个最终状态：已发现问题、已验收未发现明确差异、待确认或未处理（附原因）；分别统计覆盖数与问题数。
- 汇总、各 `review.json` 与 Excel 的问题 ID 和数量一致；每项问题都有有效来源截图、设计依据、可读的局部标注证据及并排/红色叠图链接。
- 抽查全部证据链接可打开、截图与问题描述相符，且编号、页面组和 bbox 对应正确；核实每个截图清单都有当前红色叠图链接。缺证据或配对待确认的项目不报为验收完成。
- 最终回复给出页面问题汇总和配对进度链接，并直接链接问题证据；对无明确差异的页面提供并排图链接，同时说明未配对和未覆盖范围。

## 适用范围

本流程不会自动操作手机、翻页或截图；没有可用的 Figma 连接时，不会读取设计文件中的源属性；仅凭一张 720px 设计图无法确定所有不同宽度设备的响应式规则；静态截图也不能验证动画和运行性能。遇到这些情况时，用中文说明本轮能确认的范围，并将未验证事项单独记录。
